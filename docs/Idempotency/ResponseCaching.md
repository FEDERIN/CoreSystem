# ♻️ Response Replay

CoreSystem.Idempotency stores the original HTTP response generated by a successful request.

If the same request is received again with the same idempotency key, the stored response is returned immediately instead of executing the endpoint a second time.

This guarantees that business operations are executed only once.

---

# How It Works

When a request reaches the middleware, the following sequence occurs:

```text
Client Request
       │
       ▼
Validate Idempotency Key
       │
       ▼
Compute Request Fingerprint
       │
       ▼
Lookup Storage Provider
       │
 ┌─────┴─────────────┐
 │                   │
 │ Record Exists     │ Record Not Found
 │                   │
 ▼                   ▼
Validate         Execute Endpoint
Fingerprint            │
 │                     ▼
 │              Capture Response
 │                     ▼
 │              Persist Response
 │                     ▼
 └──────────► Return Response
```

---

# What Is Stored?

The framework persists the information required to reproduce the original response.

| Property | Description |
|----------|-------------|
| Status Code | HTTP response status |
| Headers | HTTP response headers |
| Body | Serialized response body |
| Content Type | Original response content type |
| Request Fingerprint | Detects changes to the original request |
| Expiration | Determines when the record becomes invalid |

---

# First Request

The first request executes normally.

```text
POST /orders
X-Idempotency-Key: order-001
```

```
Application
        │
        ▼
Business logic executes
        │
        ▼
Response is stored
        │
        ▼
Response returned
```

---

# Duplicate Request

If the same request is received again with the same idempotency key:

```text
POST /orders
X-Idempotency-Key: order-001
```

The endpoint is **not executed**.

Instead:

```
Storage lookup
        │
        ▼
Stored response found
        │
        ▼
Stored response returned
```

This reduces unnecessary processing and prevents duplicate business operations.

---

# Fingerprint Validation

Before replaying a stored response, the middleware validates the request fingerprint.

If the fingerprint differs from the original request, the response is **not** replayed.

Instead, the middleware throws an `IdempotencyFingerprintMismatchException`.

See **Fingerprinting** and **Fingerprint Mismatch** for more information.

---

# Response Expiration

Stored responses remain available until the configured expiration period elapses.

```csharp
options.Expiration = TimeSpan.FromHours(24);
```

After expiration:

- the stored response is removed (or ignored)
- the next request is processed as a new operation

---

# Supported Status Codes

By default, the framework stores successful responses.

Default cacheable status codes:

- 200 OK
- 201 Created
- 202 Accepted
- 204 No Content

Additional status codes can be configured through `IdempotencyOptions`.

---

# Best Practices

✅ Use response replay only for operations that modify application state.

✅ Configure an expiration period appropriate for your business process.

✅ Do not reuse an idempotency key for different requests.

✅ Keep request fingerprinting enabled to prevent accidental key reuse.
